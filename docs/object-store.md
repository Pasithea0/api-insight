# Storage migration: raw events to Backblaze B2 (S3)

**Status:** implemented and unit-tested. **Not yet deployed against a live
bucket or a live database** — the runbook below is the path, and step 6 is
the verification that matters.

## Why

The `events` table grew by ~13M rows a day and was the only thing actually
filling the database host's disk. Retention had already been squeezed to
**two days** to keep the host alive, which meant two days was all the raw
history the dashboard could offer.

Three separate problems, one cause:

1. raw events cost full price to store, and the price was local disk;
2. every extra day of retention was a day closer to a full disk;
3. the thing eating the disk is the *least* structured data in the system.

## Architecture

| Concern | Lives in | Notes |
|---|---|---|
| Users, API keys, sessions | Postgres | unchanged |
| Hourly/daily rollups (`metric_buckets`, `route_buckets`, `daily_*`) | Postgres | unchanged; every chart reads these |
| Attribute key index | Postgres | rebuilt from the configured store |
| **Raw events** | **object store** when `APP_EVENT_STORE=s3` | one object per hour bucket per flush |

The object store **replaces** the Postgres `events` table, it does not mirror
it. With `APP_EVENT_STORE=s3` the table is never written: that is the whole
point, and it is what frees the disk. Postgres still holds everything else,
because those tables are small and the dashboard reads them on every load.

```
POST /v1/events ──► batch writer ──► s3 writer ──► events/dt=YYYY-MM-DD/hour=HH/NNNN.ndjson.gz
                        │
                        └──► hot source (in-memory current hour) ──► traffic / avg-duration panels

hourly ──► rollup worker ──► streams the hour back from B2, aggregates in Go ──► metric_buckets / route_buckets
```

## What an object store cannot do, and what that costs

An object store has no query engine. Every read is a listing plus a linear
decode, and that shapes the whole implementation:

- **Listing** is prefix-only, newest hour first, and stops as soon as the
  request has enough rows. `recent`, `all-events` and `search-events` all
  page newest-first with a small limit, so in practice this is a handful of
  GETs. Nothing in `internal/s3store` ever lists without a prefix — an
  unbucketed scan of a busy bucket is both slow and, on B2, billed.
- **The rollup worker** cannot `GROUP BY`, so it streams each hour back and
  aggregates in Go, including the percentiles. At ~540k events in a busy
  hour that is a few megabytes of durations held for the duration of one
  pass, which is the price of computing `percentile_cont` outside a
  database.
- **A single event** is found by deriving its hour from the timestamp
  embedded in its id, so `GET /v1/metrics/event/:id` stays one listing
  rather than a scan. See *Event ids* below.
- **Paging is exact, and takes an hour at a time.** The walk stops on an
  hour boundary and never inside one, because object keys carry no reliable
  intra-hour time order (a backdated batch is written into an older bucket
  with a newer id). An earlier implementation that stopped mid-hour returned
  an arbitrary subset of that hour — a page that looked plausible and was
  wrong. The cost is that paging into a busy hour decodes that hour; memory
  is bounded because only the newest `limit+offset` rows of an hour are
  retained.

## Event ids

Ids in the object store are generated by the writer, not by a sequence, and
they are shaped to satisfy three constraints at once:

- they must survive JSON — the dashboard puts an id in a URL and JavaScript
  parses JSON numbers as `float64`, so anything above 2^53 loses precision
  and would 404 on a perfectly good row. A 63-bit snowflake is unusable;
- they must reveal their own timestamp, so a detail lookup can be one
  listing;
- they must be recognisable as ours, so the reader can answer "not mine"
  about a row written before the switch without a lookup.

Inside 53 bits:

```
[1 marker bit][40 time bits (ms since 2024-01-01)][12 sequence bits]
```

The marker bit is what makes the third constraint exact rather than a guess:
a small Postgres integer never sets it. The 40-bit time field covers ~34
years from the epoch, which is the price of having it at all, and the
sequence handles a burst of 4096 events inside one millisecond — which
happens routinely, because the ingest handler reads the clock once per
request and a batch of 5000 events therefore shares one timestamp.

Ids are strictly increasing, borrow a millisecond on sequence overflow, and
never go backwards even if the clock does. Crucially they are never zero:
zero is the sentinel this codebase uses everywhere for "this event has no id
yet", and a naive "milliseconds since epoch" scheme hands out exactly zero
for a backfill dated before the epoch.

## Per-project retention without rewriting objects

Postgres enforces per-key retention by deleting rows and rewriting
`expires_at`. An object cannot be edited, so that approach has no equivalent
here. Instead the reader resolves each project's **current** window and drops
events older than `now - window` as it reads them.

That is not a compromise, it is closer to the intent: a shortened window
takes effect on the *next request*, with no reconciliation pass, no backlog,
and no window in which the store still serves rows the operator has already
deleted. On a retention edit in object-store mode the reconcile step is
skipped and logged as unnecessary.

Physical deletion is separate and coarser. The daily worker drops whole hour
buckets once they are older than the **longest** window any project asks for,
because an object cannot be split: if one project keeps 30 days and another
2, the buckets in between still hold the first project's events. Deleting
them early would destroy data that project was promised.

## Event store precedence

`APP_EVENT_STORE=s3` sets the default read source to `s3`, and raw-event
reads fall back in a fixed order with Postgres last, so a store error degrades
to the system of record instead of blanking the dashboard:

| Endpoint | Reads from |
| --- | --- |
| `GET /v1/metrics/recent` | configured store |
| `GET /v1/metrics/all-events` | configured store |
| `GET /v1/metrics/search-events` | configured store |
| `GET /v1/metrics/event/:id` | configured store, then the others on a miss |
| `GET /v1/metrics/export` | configured store |

The aggregate panels (`traffic`, `avg-duration`, `top-routes`, `attribute-*`,
`pattern-counts`) read the Postgres rollups when Postgres holds the events,
and stream the configured store when it does not. They are chosen by the
*default* store, not by `?store=`, which continues to govern the raw event
lists above.

The current partial hour comes from an in-memory accumulator fed by the
ingest path, because there is no events table to query for it and
re-downloading the hour from B2 every 30 seconds would be both slow and
billed. It is process-local, so startup primes it by reading the current hour
back out of the bucket once.

## Trade-offs, stated plainly

- **Up to `APP_S3_FLUSH_INTERVAL` of traffic is lost if the process is
  killed.** Events are buffered in memory before becoming an object. The
  Postgres batch writer already had a 2s window; this is the same exposure
  with a larger window, and it is the knob to turn down if that matters.
- **A bucket outage holds events in memory, then drops them.** The writer
  re-queues a failed flush and retries, but past `4 × APP_S3_MAX_BUFFER_EVENTS`
  it drops the oldest buckets with a loud log. An unbounded buffer turns "the
  bucket is unreachable" into an OOM kill, which loses everything including
  the newest events.
- **An unreachable bucket at startup is fatal.** The service refuses to start
  rather than quietly writing raw events into the database instead — that is
  precisely how the disk filled up, and it would do so while reporting a
  healthy start.
- **Boot re-reads `APP_S3_STARTUP_SCAN_HOURS` of objects.** That is what
  rebuilds rollups for hours the service was down. It is a download; lower
  the value to boot faster, at the cost of leaving a missed hour unaggregated.
- **Attribute values are compared as strings** in the object store, matching
  the Postgres path's type-sensitive jsonb containment. A numeric attribute
  filter (`{"attempts": 2}`) matches in neither store; filtering for `"2"`
  as text matches in neither either. This is faithful, not broken — but it is
  worth knowing before concluding a filter has no data.
- **Timestamps are stored at millisecond resolution.** Postgres keeps
  microseconds. `created_at` is compared and displayed at second resolution
  everywhere in the dashboard.
- **The Postgres `events` table still exists but stays empty, and nothing prunes
  it.** It is not dropped, so switching back is a configuration change rather
  than a migration. But retention follows the *configured* store, so the rows
  written before the switch never expire on their own and their pages stay
  allocated on the host whose disk is the point of this exercise. The service
  logs a hint at startup when it sees them; reclaiming them is a deliberate
  step (see [step 8](#8-then-and-only-then-reclaim-the-disk)).
- **A busy hour is a large read.** An hour's objects are fetched 8 at a time
  and decoded. Retune `APP_S3_FLUSH_INTERVAL` (fewer, larger objects vs
  fresher data) if the balance is wrong for the traffic volume.

## Runbook

### 1. Create the credentials, and do not commit them

B2 → *Application Keys* → add a key scoped to the one bucket. You need the
**key ID** and the **application key**; the application key is shown once.

Put both in the deployment's environment, never in a committed file. Nothing
in this repository contains them.

### 2. Prove the bucket is writable before switching

The service refuses to start if it cannot reach the bucket, so this is cheap
to get wrong exactly once:

```bash
aws --endpoint-url https://s3.us-east-005.backblazeb2.com \
    s3 ls s3://tidb-api-traffic/ --profile b2
```

If that lists, the endpoint, region, bucket and key are right.

### 3. Set the environment

```
APP_EVENT_STORE=s3
APP_S3_ENDPOINT=https://s3.us-east-005.backblazeb2.com
APP_S3_REGION=us-east-005
APP_S3_BUCKET=tidb-api-traffic
APP_S3_ACCESS_KEY_ID=<key id>
APP_S3_SECRET_ACCESS_KEY=<application key>
APP_S3_PREFIX=events
APP_S3_PATH_STYLE=true
```

Leave the ClickHouse variables alone. One change at a time.

Note what this does **not** change: `APP_DATABASE_URL` is still required and
the service will not start without it. Postgres still holds users, API keys
and every rollup table.

### 4. Deploy

Watch for, in order:

```
event store: raw events are written to the object store; the Postgres events table is not written
aggregation: rebuilding rollups from the configured object store, 24 hour(s) back
raw event reads configured  default_source=s3 stores=[s3 postgres] aggregate_panels_stream=true
event store: primed the partial-hour view from the object store
```

The startup scan reads nothing on the first boot (the bucket is empty) and
gets progressively more expensive as history accumulates. If it makes boot
unacceptable, lower `APP_S3_STARTUP_SCAN_HOURS`.

### 5. Confirm events are landing

```bash
aws --endpoint-url https://s3.us-east-005.backblazeb2.com \
    s3 ls --recursive s3://tidb-api-traffic/events/ | head
```

and that the bucket has a bucket for the current hour.

### 6. Verify the dashboard, from the API

Every raw-event response carries a `source` field naming the store that
answered it, which is how you confirm the switch took effect rather than
assuming it:

```bash
curl -s -b cookies.txt 'localhost:8080/v1/metrics/recent?limit=5' | jq '.source, .events[0].id'
```

- `"source": "s3"` means the object store answered.
- The id should be a large number (~10^15, up to 2^53). A small integer means
  Postgres answered, i.e. the row predates the switch.

Then check the panels that are *not* plain raw reads, because those are the
ones that had to be reimplemented:

```bash
# rollups rebuilt from the object store
curl -s -b cookies.txt 'localhost:8080/v1/metrics/traffic?range=6h' | jq '.series[-3:]'
curl -s -b cookies.txt 'localhost:8080/v1/metrics/top-routes?range=1d' | jq '.routes[0]'
curl -s -b cookies.txt 'localhost:8080/v1/metrics/attribute-keys' | jq '.keys'
```

Traffic must show a point for the current hour (from the in-memory
accumulator) and points for completed hours (from the rebuilt rollups). If
the current hour is missing but completed hours are present, the hot source
is not being fed; if completed hours are missing, the startup scan did not
run.

### 7. Verify the old rows are still reachable

Anything written before the switch is only in Postgres, and the fallback
chain is what makes it reachable. Search for something that predates the
migration:

```bash
curl -s -b cookies.txt 'localhost:8080/v1/metrics/all-events?range=2d&limit=5' | jq '.source'
```

Recent rows come from `s3`; older rows fall through to `postgres`.

### 8. Then, and only then, reclaim the disk

Once step 6 shows rollups rebuilding from the bucket and step 7 shows old rows
still reachable, the Postgres `events` table is dead weight: nothing writes it,
and retention no longer prunes it (retention follows the configured store), so
it sits on the host whose disk is the whole reason for this migration. The
service says so at startup rather than leaving you to infer it:

```
event store: the Postgres events table still holds about 13200000 rows but is no
longer written to (APP_EVENT_STORE=s3). They are dead weight on this host's disk.
```

**Look before you leap.** On a TimescaleDB hypertable — which this table becomes
whenever the extension is available — the obvious statement is the wrong one:

| Statement | On a hypertable |
|---|---|
| `TRUNCATE ONLY events;` | **fails**: `cannot truncate only a hypertable` |
| `TRUNCATE events;` | works; truncates every chunk and frees the disk |
| `VACUUM FULL events;` | runs, but the parent table is an empty shell — it reclaims **nothing** from the chunks |
| `DROP TABLE events;` | works; deletes every chunk, and the schema with it |

So, in a window, and only after backing up:

```sql
-- 1. Are these rows still wanted? This is the same cutover used in step 7;
--    if it returns rows, stop and find out why.
SELECT count(*) FROM events;

-- 2. Is it a hypertable? This decides which statement in step 3 is safe.
SELECT hypertable_name FROM timescaledb_information.hypertables
WHERE hypertable_name = 'events';

-- 3. What is it actually costing? Compare these before and after.
SELECT pg_size_pretty(pg_total_relation_size('events')) AS total,
       pg_size_pretty(pg_relation_size('events'))      AS heap,
       pg_size_pretty(pg_indexes_size('events'))       AS indexes;

-- 4. Reclaim. On a hypertable either form is fine; TRUNCATE is simpler and
--    keeps the schema (and therefore the rollback path) intact.
TRUNCATE events;
-- or, chunk by chunk, if you want the drops to be visible and interruptible:
--   SELECT show_chunks('events');
--   SELECT drop_chunks('events');

-- 5. Confirm.
SELECT pg_size_pretty(pg_total_relation_size('events'));
```

Two things worth knowing about the numbers:

- `TRUNCATE` releases the space to the operating system immediately. Unlike a
  `DELETE`, it does not leave the file allocated and does not need a `VACUUM`
  afterwards. If the disk is still full after a `TRUNCATE` that reported
  success, the space is being held by something else — check
  `pg_size_pretty(pg_database_size(current_database()))` and the rollup tables,
  not this one.
- If the database size does not fall as much as expected even after the table
  is empty, look for leftover `_timescaledb_internal` chunk tables
  (`SELECT * FROM show_chunks('events')`) and for WAL
  (`SELECT pg_size_pretty(sum(size)) FROM pg_ls_waldir()`), which retains the
  writes that filled it.

**Do not delete the Postgres deployment.** Users, API keys and every chart
live there, and the service will not start without it. What this migration
buys is that the raw stream no longer lands on that disk — not that Postgres
goes away.

## Keeping history forever

`APP_RETENTION_DAYS=0` means **unlimited**: raw events are kept forever. In
object-store mode that is exactly what it says, because object storage is
cheap and effectively unbounded:

- the reader stops filtering on age, so every event ever written stays
  readable;
- the retention pass stops dropping hour buckets entirely (it logs that it is
  doing nothing rather than listing the bucket for no reason);
- a project can still ask for a shorter window of its own, and that is still
  honoured at read time.

With the events in **Postgres**, `0` means the same thing but the consequences
are the ones this document exists because of: the `events` table grows without
bound on the database host. The service warns loudly at startup when it sees
that combination, and it is worth taking seriously.

One asymmetry to know about: switching to unlimited does not resurrect
anything already expired, and in Postgres mode rows keep whatever `expires_at`
they were stamped with when they arrived — the daily worker says so and skips
its pass. Only events ingested *after* the change are guaranteed to survive
indefinitely.

The chart range selector still tops out at a year when retention is unlimited.
That is a dropdown, not a limit: the API accepts any `days=` or `hours=` value.


## Reverting

Set `APP_EVENT_STORE=postgres` and redeploy. Nothing needs to be migrated
back:

- new events go into the `events` table again;
- the rollup worker returns to SQL aggregation automatically;
- the partial-hour cache returns to its SQL source;
- rows still in the bucket stay readable via `?store=s3`, or are simply
  ignored.

The only loss is whatever is in the bucket and not in Postgres — i.e. events
ingested between the switch and the revert.

## Testing

Hermetic by default: the object-store suite runs against an in-memory
implementation of the S3 interface, so it needs no bucket and no database.

```bash
go test ./... -count=1
```

What it covers, and why those tests exist:

- `TestQueryEventsTakesTheNewestWithinABusyHour` — regression test for the
  paging bug described above (every event in one hour).
- `TestDeleteBeforeKeepsWholeHours` — a partially-expired hour bucket is never
  deleted.
- `TestRetentionFiltersAtReadTime` — a shortened window takes effect on the
  next read.
- `TestIDSurvivesJSON` — the id survives a `float64` round trip.
- `TestIDIsNeverZeroForBackfill` — a pre-epoch backfill does not mint the
  unassigned sentinel.
- `TestStreamHourSkipsVanishedObjects` — a read racing the retention pass
  skips the vanished object instead of failing the request.
- `TestReaderNeverListsWithoutAPrefix` — the B2 cost invariant.
- `TestPercentileContMatchesPostgres` — the Go-side percentiles match
  `percentile_cont`, so the two rollup drivers store the same numbers.
- `TestCompileLikeSemantics` — the Go-side `LIKE` matches the SQL one,
  including `_`, `%`, backslash escapes and anchoring.

There is **no** integration test against a real S3 endpoint. Adding one
(a MinIO service in `docker-compose.dev.yml`, gated on an env var) is the
obvious next step; `internal/clickhouse/retention_integration_test.go` shows
the pattern this repo uses.
